### 实际28账号验收入口

在仓库外的安全配置目录准备 `b3-accounts.json`，精确28项。每项如下（ID替换为实际查询并人工核对的值；允许的空绑定填null）：

```json
{"accounts":[{"username":"实际用户名","password_env":"B3_PASSWORD_01","expected":{"user_id":101,"role_code":"CAREGIVER","org_id":205,"elder_id":null,"caregiver_id":309}}]}
```

这是结构示例，不可直接执行为28账号清单。凭据工具仍使用username和password_env；新增的expected用于验收实际身份，避免仅与错误绑定的数据库快照自证一致。

```powershell
# 明确配置ELDERCARE_DATABASE_URL，设置28个密码环境变量；不得把秘密写入命令记录或Git。
$env:ELDERCARE_PROFILE = 'B3'
$env:ELDERCARE_B3_ACCOUNT_MANIFEST = 'C:/secure-config/b3-accounts.json'
python -B -m persistence_python.security.accounts --manifest C:/secure-config/b3-accounts.json
# 只有成员4确认迁移方案、目标库和维护账号后才使用现有 --apply --admin 入口。
python -B -m persistence_python.security.verify_b3 --manifest C:/secure-config/b3-accounts.json
```

验收脚本先核验28组独立安全凭据、角色分布、护工机构关联、老人家属/机构负责人绑定及expected，再只读验证所有密码，最后逐一真实登录并解析Session，验证user_id/username/role_code/org_id/elder_id/caregiver_id和失败次数清零。输出仅统计，无密码/令牌。成功登录会正常更新登录时间并清零失败计数；账号状态或密码不符时预检终止，不主动尝试错误密码锁定正式账号。5次失败锁30分钟、停用拒绝、到期解锁的破坏性场景只在隔离测试账号执行。

预检检查接口存在、既有批次、老人社区/护工区域、在岗状态、项目上架、资质日期、指定且唯一的开放班次、班次重叠、现有及本批冲突、累计容量、机构/护工整改限制、护工账号绑定。执行时先通过各护工实际密码获得Session，再在同一工作单元创建→派单→以对应护工身份接单，逐条核对待服务/已接单和订单/护工/班次关联，成功提交后输出20组真实ID映射。通过批次事务应用锁防止同名批次并发重复执行；保留过程原有共同锁与限制检查。
