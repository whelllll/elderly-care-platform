# 3. 逻辑结构设计

## 3.1 关系模式

```text
monitor_device(device_id, elder_id, device_type, install_position, bind_time,
               unbind_time, device_status, device_sn, created_at, updated_at)

vital_sign(vital_id, device_id, elder_id, collect_time, indicator_type,
           indicator_value, is_abnormal, data_source, created_at)

emergency_event(event_id, elder_id, trigger_source, event_level, happen_time,
                response_deadline, responder_id, arrive_time, event_status,
                dispose_result, close_time, created_at, updated_at)
```

## 3.2 主键、外键与候选键

| 关系 | 主键 | 外键 | 候选键 / 唯一约束 |
|---|---|---|---|
| `monitor_device` | `device_id` | `elder_id → elder_profile(elder_id)` | `(device_sn, bind_time)`；`device_sn` 仅未解绑行唯一 |
| `vital_sign` | `vital_id` | `device_id → monitor_device(device_id)`；`elder_id → elder_profile(elder_id)` | — |
| `emergency_event` | `event_id` | `elder_id → elder_profile(elder_id)`；`responder_id → sys_user(user_id)` | — |

## 3.3 函数依赖

- `device_id → {elder_id, device_type, install_position, bind_time, unbind_time, device_status, device_sn, created_at, updated_at}`
- `(device_sn, bind_time) → device_id`；`device_sn` 单独不是键，因为同一物理设备可以有多行绑定历史。
- `vital_id → {device_id, elder_id, collect_time, indicator_type, indicator_value, is_abnormal, data_source, created_at}`
- `event_id → {elder_id, trigger_source, event_level, happen_time, response_deadline, responder_id, arrive_time, event_status, dispose_result, close_time, created_at, updated_at}`

## 3.4 范式说明

三张表都是单属性主键，非主属性完全依赖于主键，不存在部分依赖；非主属性之间也不存在传递依赖，因此均满足 3NF，实际达到 BCNF。

两处“快照”是有意保留的：

- `vital_sign.elder_id` 是采集时归属快照，不能由 `device_id` 推导（设备会解绑/重绑）；
- `emergency_event.response_deadline` 是登记时的时限快照，用于保留历史规则。

它们是事件/采集记录的属性，不构成传递依赖。

## 3.5 表数量说明

M4 实际建表 **3 张、32 个字段**；老人档案属于成员1，是 M4 的外部引用实体。若把老人档案也算入局部 E-R，则共涉及 4 个实体，但 M4 只建 3 张表。
