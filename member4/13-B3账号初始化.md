# B3 正式联调账号：精确 28 个

> 脚本：[`13_b3_accounts_28.sql`](13_b3_accounts_28.sql)  
> 密码：`Admin@123`  
> 28 个账号分别使用独立随机盐和 PBKDF2-HMAC-SHA256 哈希。

## 1. 账号分配

| 类型 | 数量 | 说明 |
|---|---:|---|
| `CAREGIVER` | 20 | 从 `caregiver` 中取全部/前 20 名在岗护工，绑定真实 `caregiver_id`、`org_id` |
| `SYS_ADMIN` | 1 | `admin` |
| `COMMUNITY_ADMIN` | 1 | `comm_admin`，绑定第一家正常机构 |
| `STREET_SUPERVISOR` | 1 | `street_sup`，不绑机构 |
| `CIVIL_SUPERVISOR` | 1 | `civil_sup`，不绑机构 |
| `ORG_MANAGER` | 2 | `org_mgr_1` 绑定 M3 在岗护工所属机构；`org_mgr_2` 绑定另一家正常机构 |
| `ELDER` | 1 | `elder_<id_card_no>`，绑定第一位正常老人 |
| `FAMILY` | 1 | `family_<id_card_no>`，绑定同一位老人 |
| **合计** | **28** | |

`org_mgr_1` 绑定的是实际 `caregiver` 在岗数据中出现最多的机构，保证机构负责人能覆盖 M3 业务；`org_mgr_2` 再选一家不同的正常机构，保证两个机构管理员不同机构。

## 2. 与 10/12 的关系

- `10` 会生成 5 个基础账号；
- `12` 会生成全部在岗护工 + 5 个老人 + 5 个家属 + 3 个机构负责人等，超过 28 个；
- **B3 是独立替代脚本，不要和 10/12 叠加执行。**

执行 B3 前，`sys_user` 必须是空表。如果已经有 10/12 生成的账号，B3 会直接 `THROW 56005`，不会产生半套数据。

## 3. 前置条件

1. 已执行 `member4/09_sys_user.sql`，`sys_user` 表存在且为空；
2. 成员3 的 `M3 BASE` 已导入，`caregiver` 至少有 20 名在岗护工；
3. 成员1 的 `service_org` 至少有 2 家正常机构；
4. 成员1 的 `elder_profile` 至少有 1 位正常老人；
5. **不需要重跑 09，也不需要重跑 M3 05。**

## 4. 执行

```bash
sqlcmd -I -S localhost -d 数据库名 -i member4/13_b3_accounts_28.sql
```

命令行必须加 `-I`；否则 `sys_user` 的筛选索引可能导致 Msg 1934。

脚本在事务中执行：

- 在岗护工不足 20 名 → 回滚；
- 正常机构不足 2 家 → 回滚；
- 没有正常老人 → 回滚；
- 实际插入不是 28 条 → 回滚。

## 5. 自测

```sql
SELECT COUNT(*) AS total_accounts FROM dbo.sys_user;
-- 期望 28

SELECT role_code, COUNT(*) AS account_count
FROM dbo.sys_user
GROUP BY role_code
ORDER BY role_code;

SELECT username, role_code, org_id, elder_id, caregiver_id
FROM dbo.sys_user
ORDER BY user_id;

SELECT COUNT(DISTINCT password_salt) AS distinct_salts,
       COUNT(DISTINCT password_hash) AS distinct_hashes
FROM dbo.sys_user;
-- 期望都是 28
```

身份绑定检查：

- `CAREGIVER`：`caregiver_id` 非空，且对应真实护工；
- `ELDER` / `FAMILY`：`elder_id` 非空，且指向同一位老人；
- `ORG_MANAGER`：两个账号的 `org_id` 必须不同；
- `COMMUNITY_ADMIN`：`org_id` 非空；
- `STREET_SUPERVISOR` / `CIVIL_SUPERVISOR`：不绑老人/护工。
