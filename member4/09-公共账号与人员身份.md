# 公共账号与人员身份（sys_user）

> 一张表保存“登录账号 + 人员身份”；一人一角色。
>
> 负责人：成员4　｜　18 个字段　｜　8 个角色

## 1. 这张表解决什么

`sys_user` 是公共共享表，其他模块不再各自建用户表，只引用 `user_id`：

| 引用方 | 字段 |
|---|---|
| M1 能力评估 | `assessor_id → sys_user.user_id` |
| M4 应急事件 | `responder_id → sys_user.user_id` |
| M5 补贴审核/抽查/整改 | `current_auditor_id`、`auditor_id`、`inspector_id`、`reviewer_id`、`create_by` |
| M6 日志 | `sys_user` 自身的 `user_id` |

老人档案、护工档案、机构信息仍在各自表中，本表只存外键，不重复保存姓名、身份证、证书等业务字段。

## 2. 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | INT IDENTITY | 主键 |

| `password_salt` | VARCHAR(64) | 每用户独立盐 |
| `real_name` | NVARCHAR(50) | 真实姓名 |
| `phone` | VARCHAR(20) | 手机号 |
| `email` | VARCHAR(100) | 邮箱 |
| `role_code` | NVARCHAR(30) | 角色，一人一角色 |
| `org_id` | INT | 所属机构，FK → `service_org` |
| `elder_id` | INT | 绑定的老人，FK → `elder_profile` |
| `caregiver_id` | INT | 绑定的护工，FK → `caregiver` |
| `user_status` | NVARCHAR(10) | 正常、停用、锁定 |
| `login_fail_count` | INT | 连续登录失败次数，0–5 |
| `lock_until` | DATETIME2(0) | 锁定截止时间 |

## 3. 八个角色

| role_code | 角色 | 身份绑定 |
|---|---|---|
| `COMMUNITY_ADMIN` | 社区管理员 | `org_id` 必须 |
| `ELDER` | 老人 | `elder_id` 必须 |
| `FAMILY` | 老人家属 | `elder_id` 必须 |
| `CAREGIVER` | 护理员 | `caregiver_id` 必须 |
| `ORG_MANAGER` | 机构负责人 | `org_id` 必须 |
| `STREET_SUPERVISOR` | 街道监管 | 不绑老人/护工 |
| `CIVIL_SUPERVISOR` | 民政监管 | 不绑老人/护工 |
| `SYS_ADMIN` | 系统管理员 | 不绑老人/护工 |

约束 `CK_user_role_identity` 会强制检查“角色和身份匹配”，不能出现“护理员没绑护工”或“社区管理员绑了老人”。

## 4. 固定权限矩阵

权限不落库，写在服务层常量里；`sys_user.role_code` 决定角色，数据范围在查询/接口层过滤。

### 方案 A：简化数据范围（当前采用）

`sys_user` 只有 `org_id`、`elder_id`、`caregiver_id`，没有社区/街道/区县字段，所以当前不实现“本社区、本街道、本区县”的精确隔离。

| 角色 | 能做 | 数据范围（方案 A） |
|---|---|---|
| 社区管理员 | 建档、评估、计划、代下单、派单、补贴初审；登记/响应事件 | 不做社区过滤；保留社区业务与初审权限 |
| 老人 | 本人档案/订单/体征/补贴查看，本人下单、确认、上报 | `elder_id` = 本人 |
| 老人家属 | 绑定老人查看、代下单、确认、评价 | `elder_id` = 绑定老人 |
| 护理员 | 接单、签到签退、服务记录、上报、响应自己的事件 | `caregiver_id` = 本人 |
| 机构负责人 | 本机构护工、证书、排班、工时、整改；响应事件 | `org_id` |
| 街道监管 | 街道复审、整改复查、抽查 | 不做街道过滤；全局只读 + 授权审核写操作 |
| 民政监管 | 民政终审、抽查、拨付 | 不做区县过滤；全局只读 + 授权审核写操作 |
| 系统管理员 | 账号、角色、日志、备份、系统配置 | 全局，业务只读 |

代码判断顺序：

```text
登录 → 取 role_code
     → 判断角色能不能做这个动作
     → 只看 elder_id / caregiver_id / org_id
     → 社区、街道、区县暂不做精确过滤
```

**方案 A 不提供行政区域级数据隔离，这是当前课程设计的简化范围。** 如果以后老师要求精确到社区/街道/区县，再给 `sys_user` 加辖区字段或增加“账号—辖区”关联表，不能只改文档。

### 审核任务分配（成员5）

成员5 的审核/抽查/复查任务通过以下字段分配给具体账号：

```text
subsidy_application.current_auditor_id
subsidy_audit_log.auditor_id
quality_inspection.inspector_id
rectification.reviewer_id
```

这些字段都指向 `sys_user.user_id`（成员5 的 `02` 已核验外键）。规则：

- 登录用户只能处理 `current_auditor_id` / `auditor_id` / `inspector_id` / `reviewer_id` 等于自己的任务；
- 不是分配给自己的审核任务，后端返回 403；
- 街道监管、民政监管虽然不做普通业务写入，但可以执行各自被授权的街道复审、整改复查、抽查操作；
- 审核任务分配本身由业务流程完成，不能靠前端传入 `user_id` 冒充。

### Session 约定

登录后 Session/JWT 至少包含：

```text
user_id
username
real_name
role_code
org_id
elder_id
caregiver_id
```

建议：30 分钟无操作过期，最长 8 小时；`sys_user` 不存 Session，由 Python 登录层维护。

### 密码哈希口径

`password_salt` 和 `password_hash` 都按 Base64 存储：

```text
password_salt = Base64(16 字节随机盐)
password_hash = Base64(PBKDF2-HMAC-SHA256(password, salt, 100000 次))
```

Python 登录校验：

```python
import base64, hashlib

def verify(password: str, password_hash: str, password_salt: str) -> bool:
    salt = base64.b64decode(password_salt)
    expected = base64.b64encode(
        hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt, 100000)
    ).decode()
    return expected == password_hash
```

测试账号统一用 `Admin@123` 和同一组演示盐/哈希，方便联调；正式环境必须每个账号独立随机盐，不能复用演示值。

补充业务账号（`12`，主测试场景约 37 个，已存在的会跳过）：

| 类型 | 最多数量 | 关联方式 |
|---|---:|---|
| 护理员 | 全部在岗（主场景 20） | `caregiver` 实际在岗记录 |
| 老人 | 5 | `elder_profile.id_card_no` 唯一业务键 |
| 家属 | 5 | 同上，一位老人一个家属账号 |
| 机构负责人 | 3 | `service_org(org_name, org_address)` 唯一业务键 |
| 社区审核 | 2 | `service_org` 第 2、3 家正常机构 |
| 街道/民政审核 | 2 | 不绑定机构 |

`12` 不写死 `elder_id`、`caregiver_id`、`org_id`；都从实际业务数据 `INSERT ... SELECT` 关联。

## 6. 已知集成点

- `service_org` 目前由成员1 维护，字段是养老服务机构；街道/民政账号暂不强制 `org_id`，辖区范围后续由机构表扩展或应用层配置。
- 成员3 的 `caregiver` 表已合并 main（`caregiver_id INT` 主键）；如果 `09` 执行时它已存在，外键会自动加，`11` 只作补充。
- 如果以后要“一人多角色”，再增加 `sys_user_role` 关联表，`sys_user.role_code` 改为角色主表外键；当前课程设计保持一人一角色。
