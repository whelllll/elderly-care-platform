# 后端开发任务及具体实现要求（修订版）

## 一、Python 持久层设计与实现（Persistence Layer）

### 1. 实现目标

建立 Python 后端与 SQL Server 数据库之间的统一数据访问层，为各业务模块提供标准化的数据访问接口，实现数据库连接、数据操作、事务管理及跨模块业务接口对接。

### 2. 具体功能要求

**（1）数据库连接管理**

- 使用 Python、SQLAlchemy 和 pyodbc 连接 SQL Server。
- 统一管理数据库连接、Session 和连接释放。
- 数据库连接参数通过环境变量配置。
- 提供统一的数据库连接模块 db.py。
- 支持连接异常处理。

**（2）数据模型设计**

- 根据正式数据库数据字典建立 ORM 模型。
- 保证模型字段、数据类型、主外键关系与 SQL Server 实际结构一致。
- 按业务模块划分 models 文件。

**（3）DAO 数据访问层**

- 按业务模块划分 DAO。
- 实现常用 CRUD 操作。
- 支持分页查询、条件查询和必要的多表关联查询。
- 使用参数化 SQL，避免 SQL 注入。
- 对外提供统一的数据访问接口。

**（4）事务管理**

- 支持事务开启、提交和回滚。
- 多步骤业务操作保证事务原子性。
- 操作异常时正确回滚。
- 跨模块业务操作遵循数据库存储过程规定的事务及锁定机制。

**（5）业务接口对接**

- 对接成员1—5的正式数据库表、视图及存储过程。
- 完成成员2服务项目、订单、派单等业务的数据访问接口。
- 对接成员5的整改限制视图、统一加锁过程及相关业务接口。
- 正确处理存储过程的输入参数、输出参数及异常结果。

### 3. 验收标准

- Python 成功连接 SQL Server。
- 各模块 DAO 能够正常执行数据操作。
- CRUD 操作结果正确。
- 事务提交、回滚正常。
- 存储过程和视图能够正常调用。
- ORM 模型与正式数据库结构一致。

## 二、用户登录与 Session 安全管理（Authentication）

### 1. 实现目标

实现统一的用户身份认证机制，完成账号密码验证、账号状态检查、登录失败锁定及 Session 生命周期管理。

### 2. 密码哈希要求

统一采用 PBKDF2-HMAC-SHA256。

正式账号密码安全要求：

- 哈希算法：PBKDF2-HMAC-SHA256。
- 迭代次数：100000 次。
- 每个正式账号独立生成 16 字节随机盐值。
- password_salt 和 password_hash 均使用 Base64 编码存储。
- 登录时根据数据库保存的盐值重新计算哈希并验证。
- 不保存明文密码，不使用固定盐值。

演示测试账号例外：

- 仅在与B3正式联调账号隔离的独立临时测试环境中，允许演示账号使用统一演示密码 Admin@123，并共用一组演示盐值及哈希值。

- 该例外不得用于B3正式联调环境及其28个测试账号。

- B3的28个正式联调账号必须分别生成独立的16字节随机盐值，并根据各自密码单独计算对应哈希值。

- 28个账号不得共用盐值、哈希值，也不得直接使用演示账号的共享凭据。

- 正式账号注册和密码修改必须重新生成独立随机盐值及对应哈希。

### 3. 登录验证要求

- 根据 username 查询用户，不使用固定 user_id 登录。
- 账号停用时拒绝登录。
- 账号仍处于锁定时间内时，即使密码正确也拒绝登录。
- 连续登录失败达到 5 次时，立即锁定 30 分钟。
- 锁定期间重复尝试不延长锁定时间。
- 锁定到期后解除锁定、清零失败次数，再验证本次密码。
- 登录成功后清零失败次数。
- 登录成功后更新最后登录时间。
- 账号停用状态不会因锁定到期而自动解除。

### 4. Session 管理要求

Session 由 Python 登录层维护，不存储在业务数据库中。

Session 至少包含：

- user_id：用户编号。
- role_code：角色编码。
- org_id：所属机构编号。
- elder_id：老人编号。
- caregiver_id：护工编号。

有效期要求：

- 30 分钟无操作自动过期。
- 最长有效时间为 8 小时。
- 任一过期条件满足后，Session 失效。
- Session 失效后必须重新登录。
- 退出登录时主动使当前 Session 失效。

### 5. 验收标准

- 正确账号密码能够登录。
- 错误密码能够累计失败次数。
- 连续失败 5 次后锁定 30 分钟。
- 锁定期间正确密码也无法登录。
- 锁定到期后能够重新登录。
- 停用账号无法登录。
- 登录成功后 Session 身份字段完整。
- 30 分钟空闲过期和 8 小时最长有效期均有效。
- 28个B3账号均使用独立安全密码、随机盐及对应哈希。
- 28个B3账号均能够正常通过 Python 登录模块完成身份认证。
- 登录后的角色及 Session 身份字段与数据库中的账号绑定关系一致。
- 隔离测试通过与正式B3账号验收通过应分别记录，不得混淆。

## 三、RBAC 角色权限与数据范围控制（Authorization）

### 1. 实现目标

建立统一的后端权限控制机制，根据当前登录用户的角色、身份及授权数据范围，判断用户是否具有相应的业务操作权限和数据访问权限。

权限校验统一放在后端，不能仅依赖前端隐藏按钮。

### 2. 角色权限要求

采用简化 RBAC 方案，根据当前登录用户的 role_code 判断业务操作权限。

| 用户角色          | 功能权限                                                |
| ----------------- | ------------------------------------------------------- |
| ELDER             | 查看本人数据、提交问题上报                              |
| FAMILY            | 查看通过 sys_user.elder_id 绑定的老人数据、提交问题上报 |
| CAREGIVER         | 接单、执行服务及完成本人业务闭环                        |
| ORG_MANAGER       | 处理本机构业务及完成业务闭环                            |
| COMMUNITY_ADMIN   | 保留建档、派单、社区初审等原有业务权限                  |
| STREET_SUPERVISOR | 普通业务只读，允许补贴复审、整改复查                    |
| CIVIL_SUPERVISOR  | 普通业务只读，允许补贴终审、质量抽查                    |
| SYS_ADMIN         | 按成员4最终确认的系统管理员权限执行                     |

具体业务操作权限以小组最终确认的权限矩阵为准，不允许仅根据角色名称扩大权限。

### 3. 后端权限校验

- 所有需要身份认证的业务接口必须检查登录状态。
- 根据当前 Session 获取用户身份和角色。
- 每次业务操作前检查当前角色是否拥有相应权限。
- 不允许通过修改请求参数冒充其他角色或用户。
- 无权执行的操作返回 HTTP 403。
- 未登录或 Session 失效返回 HTTP 401。
- DAO 层保留必要的身份及数据范围校验，防止绕过业务入口直接操作数据。

### 4. 数据范围控制

第一版正式采用方案A，不修改现有数据库表结构，不新增社区、街道、区县字段或关联表。

具体要求：

（1）ELDER

- 根据当前 Session 中的 elder_id 限制本人数据。
- 不允许访问其他老人的个人数据。

（2）FAMILY

- 根据现有 sys_user.elder_id 字段建立的家属与老人绑定关系确定可访问的老人数据。
- 查询时校验当前登录用户的 sys_user.elder_id 与目标 elder_id 是否匹配。
- 不允许仅凭请求参数传入 elder_id 访问其他老人数据。
- 第一版不新增额外家属授权关系表，直接使用现有 sys_user.elder_id 实现数据范围控制。

（3）CAREGIVER

- 根据当前 Session 中的 caregiver_id 限制本人护工数据。
- 不允许访问其他护工的个人业务记录。

（4）ORG_MANAGER

- 根据当前 Session 中的 org_id 限制本机构数据。
- 不允许访问其他机构的数据。

（5）COMMUNITY_ADMIN、STREET_SUPERVISOR、CIVIL_SUPERVISOR

- 暂不实现本社区、本街道、本区县的精确数据过滤。
- 不新增行政区域字段或关联表。
- 按各自明确授权的业务权限及审核任务分配关系控制操作。

（6）SYS_ADMIN

- 按成员4最终确认的系统管理员权限执行，不默认扩大普通业务写权限。

特别说明：方案A不提供行政区域级数据隔离，这是当前课程设计的简化范围。

### 5. 审核人员身份与任务分配安全

- 当前操作人员身份统一从服务端 Session 获取。
- 不允许前端自行指定其他用户的 user_id 作为操作人。
- 补贴审核涉及 auditor_id，整改复查涉及 reviewer_id，质量抽查涉及 inspector_id。
- 开发前必须核对成员5正式数据库表结构、数据字典及相关SQL代码，确认上述字段的实际业务含义。
- 重点确认 auditor_id、reviewer_id、inspector_id 是否表示预先分配的任务处理人员，还是仅记录实际执行审核、复查、抽查操作的人员。
- 核实上述字段与 sys_user.user_id 或其他人员编号之间的关联关系，确认能够正确映射后再进行身份比较。
- 如果上述字段仅用于记录实际操作人员，不能直接将其作为任务预分配依据，也不能据此判断任务是否分配给当前登录用户。
- 登录用户只能处理明确分配给自己的对应审核任务，任务归属必须具有真实、明确的数据库依据。
- 审核、抽查、复查业务入口中的操作人员身份统一从当前服务端 Session 获取，不允许前端自行指定。
- 如果成员5现有数据库结构无法提供明确的任务分配依据，应先与成员5确认现有实现方式，不得直接假设操作人字段就是任务分配字段。
- 审核单位名称由后端配置提供，不直接使用用户名代替。
- DAO 层保留身份及任务分配校验，防止绕过业务入口冒充其他操作人员。

### 6. 验收标准

- 不同角色只能执行明确授权的业务操作。
- 未登录请求返回 HTTP 401。
- 已登录但无权执行的请求返回 HTTP 403。
- 老人不能访问其他老人的数据。
- 家属不能访问未通过 sys_user.elder_id 绑定的老人数据。
- 护工不能访问其他护工的个人业务数据。
- 机构负责人不能访问其他机构的数据。
- 街道和民政不能执行未授权的普通业务修改。
- 在数据库存在明确任务分配依据且完成字段映射核验的前提下，街道只能执行分配给自己的整改复查。
- 在数据库存在明确任务分配依据且完成字段映射核验的前提下，民政只能执行分配给自己的质量抽查及其他明确授权的审核操作。
- 审核人员不能处理分配给其他人的任务。
- 不得将仅记录实际操作人的 auditor_id、reviewer_id、inspector_id 直接作为任务预分配依据。
- 如果现有数据库结构无法判断任务归属，应在联调前明确记录该限制，不得将尚未实现的任务分配校验标记为通过。
- 操作人员身份由后端自动获取，不能由前端冒填。
- 不配置、不实现社区、街道、区县精确数据过滤。
- 不新增数据库字段或关联表。
