# 成员3护工与排班管理业务需求分析

## 个人报告可用概述

本模块面向服务机构负责人、护理员、社区服务管理员及工时审核人员，管理护工档案、项目资质、排班与有效工时。机构负责人维护人员、证书及班次，系统校验排班时间有效性和未取消班次重叠。管理员经成员2派单接口调用成员3校验，在同一事务内核对在岗、资质、社区、班次覆盖、容量及服务冲突，派单以排班编号固定班次。护工在已接单的有效派单下签到签退，系统核对位置并计算实际时长；定位缺失、越界或格式异常转人工审核。审核通过且认可工时明确的记录才计入统计，异常通过须保留审核说明及原围栏结果。工时与派单的班次必须一致；审核人员的正式权限归属仍待确认。

系统边界内为成员3职责。成员2派单模块以矩形框中的 `«actor»` 标注表示外部系统参与者，与内部“校验护工资格与排班”用例采用实线关联。社区服务管理员仍关联系统边界外的“发起派单（成员2业务）”上下文用例，成员2派单模块也关联该上下文用例；该用例仅说明业务发起来源，不属于成员3功能，也不再另画成员2系统边界。参与者关联不是系统间调用的时序图，不表达管理员直接访问成员3内部控制。

“审核工时记录”作为基础用例，涵盖通过或驳回的审核结果。“异常工时人工复核”通过虚线、开放箭头的 `«extend»` 关系指向“审核工时记录”，在定位缺失、越界或格式异常需要人工核实时扩展基础审核行为。条件成立时必须执行复核；人工复核既可能通过，也可能驳回，不保证一定产生认可工时。图中保留原审核权限待确认标注。

用例图已移除跨越两个系统边界的 `«include»`，不新增其他包含关系。其余参与者及业务用例保持原义。三张鲁棒图及其说明保持原业务设计，审核控制仍可执行认可或驳回，与修订后的基础用例一致。

## 图2 排班管理鲁棒图

对应文件：`成员3_排班管理鲁棒图.drawio`、同名 PNG 与 SVG。

服务机构负责人通过排班维护边界对象提交创建或修改请求。排班管理控制核对护工档案，并调用时间与冲突校验控制，读取已有排班。结束时间必须晚于开始时间；同一护工未取消的排班区间不得重叠，采用左闭右开区间，允许相邻班次首尾衔接。修改时排除自身，恢复排班也需重新检查。

校验和保存处于同一事务，全部通过才保存，否则返回拒绝原因且不保存。取消排班应保护已有派单关联，具体可变范围按小组确认的更正规则落实。本图不展开成员2的派单业务。

涉及实体：护工档案 `caregiver`、排班信息 `caregiver_schedule`。护工存在性由外键等参照约束保证；时间先后和正容量可由行内 CHECK 实现；跨行排班重叠须通过事务、锁、存储过程或触发器保证，不能写成普通 CHECK。

## 图3 派单前资格与排班校验鲁棒图

对应文件：`成员3_派单前校验鲁棒图.drawio`、同名 PNG 与 SVG。

社区服务管理员通过成员2的派单边界提交请求，由成员2的派单事务控制读取订单预约与时长快照，调用成员3校验控制。校验内容包括：护工在岗；证书状态有效且预约开始日期在有效期内；证书对应订单服务项目；订单社区与护工标准社区精确匹配；目标班次开放；班次护工与派单护工一致；完整预约区间位于班次内；容量未满；同一护工不存在服务时间重叠的有效派单。

容量直接按 `dispatch_record.schedule_id` 关联班次，按派单去重计数。待接单、已接单占用容量，拒绝和撤回释放，已完成仍累计，不通过预约时间反推班次。服务冲突检查仍须跨该护工所有有效派单进行，不能仅因班次编号不同就放行。

虚线框强调成员2统筹的**同一个数据库事务**：读取及加锁、成员3校验、成员2写入派单，最后一次提交；任一失败整体回滚。成员3返回校验结果，不单独提交派单。框是事务协作范围的注释，不是新的系统或数据实体。

涉及实体：成员3的 `caregiver`、`caregiver_certificate`、`caregiver_schedule`；成员2的 `service_order`、`service_item`、`dispatch_record`。`dispatch_record.schedule_id → caregiver_schedule.schedule_id` 是已确认接口。外键可保证班次存在，但班次护工一致、服务区间覆盖、容量与服务冲突等须在同一事务中联合校验。

## 图4 签到签退与工时审核鲁棒图

对应文件：`成员3_签到签退与工时审核鲁棒图.drawio`、同名 PNG 与 SVG。

护工通过签到签退边界提交时间和位置。签到控制核对已接单的有效派单、所属班次和护工；首次签到创建工时，签退更新同一记录，每条派单最多一条工时。`work_record.schedule_id` 必须等于 `dispatch_record.schedule_id`，对应班次护工须与派单护工一致；这些跨表条件由事务联合验证。

核算控制读取订单地点、WGS84 坐标及签到半径，解析实际位置字符串并计算距离。围栏通过的记录进入常规审核；定位缺失、格式无效或无法计算时保存“待校验”，越界保存“未通过”，均转人工审核。签退必须晚于签到，认可完整分钟非负且不得超过实际时间间隔。审核通过须已有必要的签到签退条件并明确 `effective_minutes`；定位异常的通过决定必须具有非空白 `review_note`，原异常 `fence_result` 不得改成“通过”。签退位置缺失或无效同样需要人工核实。

审核人员通过审核边界查看待审数据并提交决定、认可分钟及说明。统计控制只汇总 `review_status = N'通过'` 且 `effective_minutes IS NOT NULL` 的记录；待审核和驳回记录的有效工时保持 NULL，不按零分钟冒充已认可工时。月度归属按签到日期，跨月不拆分。

涉及实体：成员2的 `dispatch_record`、`service_order`，成员3的 `caregiver_schedule`、`work_record`。图中签到控制从派单与班次核对护工编号，因此无需为此新增实体或在工时表重复保存护工编号。

## 跨模块职责与一致性核对

| 核对项 | 四张图的统一口径 |
| --- | --- |
| 成员3数据范围 | 保持 v3 的四张业务表、32个字段；图示未新增表、字段或权限。 |
| 派单及事务 | 成员2负责派单入口、事务协调与派单写入，成员3提供校验。 |
| 班次归属 | 派单显式保存 schedule_id；工时班次与派单相同；容量直接按该外键统计。 |
| 工时统计 | 只统计审核通过且工时明确的记录；未完成必要签退条件不得认定通过。 |
| 异常审核 | 保存原围栏结果、审核决定和审核说明；审核人员权限待确认。 |
| 订单状态 | 签到开始、服务完成等订单状态通过成员2接口协调；工时审核不替代任务书要求的家属确认或双方签字。 |

鲁棒图使用带 `«boundary»`、`«control»`、`«entity»` 构造型的对象框。参与者只接触边界对象，边界对象调用控制对象，控制对象协调其他控制并访问实体；没有参与者直接访问数据库，也没有边界对象直接修改实体。交互线及编号帮助解释对象职责，不表示 E-R 联系基数或严格的时序建模。

## 资质规则定稿与现有图示复核

资质规则采用数据字典v4：一名护工可持多张证书，同一护工同一张证书只授权一个服务项目，UNIQUE(caregiver_id, certificate_no)。不同项目可分别登记不同证书。派单仍按护工、订单service_id、证书有效状态及预约日期进行资格校验；一次有效匹配即可满足该项目资质，不改变资格校验用例或控制对象职责。

局部E-R图v3保留护工1:N资质证书和单值服务项目编号属性，没有同一证书对多项目的联系或文字。用例图v2只表达档案、资质维护与校验目标；三张鲁棒图未把同一证书按项目展开成多行，因此与定稿规则不冲突，不重新绘图。图形结构及既有联系不变，本说明更新为v3以同步文字依据。原始图中未展示的证书组合唯一约束以数据字典v4为准；后续测试夹具应同步新唯一键，避免旧多项目样例。

## 公共机构及派单接口同步说明

护工以 org_id INT NOT NULL 引用成员1负责的公共 service_org(org_id)，名称经关联查询取得。仍为四表32字段；不新增审计字段或业务用例。用例图及三张鲁棒图未描述机构名称存储细节，保持原图，仅E-R图更新机构属性和外部引用注释。

成员2最终接口使用 service_item.status 仅限制新订单创建；已存在订单不因项目下架而阻止派单、接单或履行；dispatch_record.schedule_id 引用班次；order_id 不设普通UNIQUE，最多一条有效派单由成员2筛选唯一索引保证。容量直接按 schedule_id，工时 dispatch_id 引用派单；原资格、时间覆盖、工时审核与同事务协作不变。公共机构表最终DDL仍待成员1提供，尚未联调。


## 已确认接口更新

CHECKIN先生成与真实派单及班次匹配的待审核签到，签退及有效分钟为空；成员2START只要求匹配的签到记录，不要求签退或审核通过。随后FINALIZE更新同一work_record，不新增第二条。服务项目下架只限制创建新订单，不影响已有订单继续履行。

现有鲁棒图历史标签“服务项目上架状态”不再表示派单阻断条件；当前解释以本次确认规则为准。本轮未改图形文件，后续绘图修订时可将该标签同步为“既有订单项目与时长快照”。
