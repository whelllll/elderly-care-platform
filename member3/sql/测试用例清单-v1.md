# 成员3测试用例与数据准备清单 v1

本阶段保持数据字典v4的四表32字段，不修改01—04、原README、其他成员资料或GitHub。现有README是建表阶段记录，最新测试进度以本清单及《测试执行结果-v1.md》为准。

## 文件和执行顺序

1. `05_M3_TestData.sql`：两阶段合法数据生成方案。默认 `@AllowWrite=0`，仅输出依赖。父表和业务键确认后，在专用整合库将其设为1，先执行BASE；不要在正式库执行。
2. BASE提交后，将输出的护工和排班清单交给成员2，由其接口创建订单及已接单派单。成员3不替成员2插入或更新其表。
3. 成员2准备完成后，将05的 `@Stage` 改为WORK再运行。必须满足全部20条前置条件，否则整体回滚。使用动态查询取得真实自增编号，不填固定主键。
4. `06_M3_ConstraintTests.sql` 可在当前独立库直接执行，仅创建会话临时表。复制01的同名列和PK/UQ/CHECK/DEFAULT定义；不复制FK，没有替代成员1/2父表。59例每例独立事务，全部回滚。结论限于该隔离副本的声明式约束行为，不等于真实dbo联调。
5. `07_M3_IntegrationFKTests.sql` 默认关闭真实写入。待05批次与六条成员3外键就绪后开启，逐项对指定测试记录更新为查证不存在的父键值，以547错误及目标约束名判定通过，随后回滚。缺表、缺批次、缺可信外键均标SKIP。
6. 完成整合后重新运行04的严格外键检查，再记录真实测试结果。成员2的两条反向外键本阶段只读取状态，不写其表。

## 成员1/2必须提供的前置条件

- 成员1：真实service_org最终DDL和供测试使用的机构业务键。05以统一字典中的org_code查询；若成员1最终未采用该列，必须先确认其稳定且唯一的业务键，再调整查询，不能填猜测的org_id。机构应为允许承接服务的测试机构。
- 成员2：最终版service_item表及一个已上架测试项目的(service_name, service_type)。当前仓库早期脚本尚未完全对齐最终派单接口，须先补齐最终dispatch_record.schedule_id及相应外键，不由成员3代改。
- 部署两条BASE外键：caregiver.org_id→service_org；资质service_id→service_item。WORK前补齐工时→派单外键，以及成员2派单→护工/班次的反向关联；确认均启用可信且NO ACTION。
- 成员2按BASE输出，给护工01—20各准备且仅准备1条 `remark=N'M3T2030联调专用'` 的派单，状态已接单，订单已进入服务中。预约落在该护工开放班次内，项目与测试项目相同，时长1—240分钟。
- 订单地址使用“清华园社区-详细地址”（如配置改变则同步），经纬度及允许半径同时齐全，纬度[-89,89]、经度[-180,180]、半径1—1000米。范围收窄是为了生成可解释的越界样例，不改变数据库正式约束。
- 候选派单不存在已有工时，有有效证书、班次护工一致、完整覆盖时间，无其他有效服务重叠，容量不超限；05在事务内查询核对，不宣称已具有生产并发防护。
